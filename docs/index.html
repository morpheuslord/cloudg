cloud graphing · AWS / Azure / GCP

Map the cloud. Scan it. Merge everything.

cloudg collects your infrastructure into a graph, fans out to the security scanners you already trust, and merges every finding against 28 compliance frameworks. It can also skip the scanning entirely: aggregate outputs you already have, or map the complete inventory, every service interlinked, with no scanner involved.

Installation

# core: graph engine, normaliser, renderers, ingest
pip install cloudg

# cloud SDK extras, pulled in only for collection
pip install cloudg[aws]        # boto3, aioboto3
pip install cloudg[azure]      # Azure management SDKs
pip install cloudg[gcp]        # google-cloud-asset, google-auth
pip install cloudg[mcp]        # the official MCP SDK, see MCP server
pip install cloudg[all]        # all of the above

The core package alone ships the graph engine, ontology builder, findings normaliser, report renderers and cloudg ingest. That is enough to aggregate existing scan results on a machine with no cloud access at all.

The scanners are not Python dependencies. Prowler, ScoutSuite, Checkov and Trivy are separate executables. Install whichever subset you want; cloudg checks PATH at run time and skips anything missing with a warning. install.sh / install.bat set up all of them, and the Docker image bundles the four binaries.

Requires Python 3.11 or newer.

The pipeline

collect -> graph -> scan -> normalise -> report
                \-> ontology / RAG / terraform

Collection runs all configured providers concurrently with asyncio, iterating accounts and regions per provider. Regions auto-discover with --regions all. Assets and network edges go into a directed NetworkX graph: BFS from the internet node finds exposed resources, and blast-radius scoring estimates what an attacker could reach from each node.

The enabled scanners run in parallel over the same inventory, each in its own thread with its own timeout. Their findings, the graph's reachability findings and the built-in IAM linter's results all flow into the normaliser, which deduplicates within and across scanners, rescores against CVSS, and maps everything to compliance controls.

Every phase degrades gracefully. A missing binary, an unreachable provider or a failed exporter logs a warning; nothing else stops.

Alongside the pipeline sits an independent function: inventory mapping. It runs no scanners at all. It deep-collects everything deployed or default across every service, links it into one map, and lets scanner findings merge into that map later.

cloudg run

The full pipeline: collect, graph, scan, normalise, report.

cloudg run -p aws --regions us-east-1
cloudg run -p all --regions all
cloudg run -p aws --scanners prowler,trivy
cloudg run -p aws --regions us-east-1 --terraform
FlagMeaning
-p, --provideraws, azure, gcp or all; repeatable
--regionsall for auto-discovery, or a comma-separated list
--scannerssubset of prowler,scoutsuite,checkov,trivy,iam; defaults to scanners.enabled
--iac-dirdirectory for the IaC scanners (Checkov, Trivy fs)
--imagescomma-separated container images for Trivy
--ontology / --no-ontologyRDF export, on by default
--rag-export / --no-rag-exportRAG chunks, on by default
--terraform / --no-terraformTerraform recreation, off by default
-o, --outputoutput directory, ./reports by default

When no IaC directory is configured but --terraform is on, the IaC scanners target the generated Terraform recreation of the live infrastructure. Checkov then audits your actual cloud, not whatever directory cloudg happens to run from. There is deliberately no fallback to .: a zero-finding scan of an unrelated directory reads like a clean bill of health, and cloudg refuses to produce one.

collect & scan

The phases alone. collect writes assets and edges without running a scanner; scan runs the selected scanners concurrently and writes raw-findings.json, no collection.

cloudg collect -p aws --profile prod --region eu-west-1
cloudg scan -p aws --scanners prowler,checkov --iac-dir ./terraform

cloudg map

Scanner-independent inventory mapping: what exists, and how is it wired together. What is wrong stays the scanners' business. No scanner runs and none needs to be installed; read credentials are enough.

cloudg map -p aws --regions all
cloudg map -p aws --org --regions all                        # every account in the Organization / Control Tower
cloudg map -p aws --org --ou Workloads --exclude-account 111122223333
cloudg map -p aws --services containers,serverless,security   # narrow the run
cloudg map -p all --regions all
cloudg map -p aws --findings ./reports/raw-findings.json      # overlay scanner output

Coverage comes in four layers:

LayerWhat it adds
Deep collectorsgrouped into families selectable with --services: network (VPC fabric, transit gateway attachments, VPC endpoints, ALB/NLB listeners and target groups), compute (EC2, Auto Scaling, launch templates), containers (ECR, ECS services and task definitions, EKS nodegroups, Fargate, addons, access entries, pod identity), kubernetes (workloads, services, ingresses and service accounts inside EKS), serverless (Lambda triggers and URLs, API Gateway, Step Functions), integration (SQS, SNS, EventBridge, Kinesis), storage/data, identity (the IAM graph), security (GuardDuty, Security Hub, Inspector coverage, Macie, Config, Access Analyzer, Detective, WAF, Network Firewall, Shield), logging, dns, iac (CloudFormation stacks and what they manage). Account-wide services run once per account; disabled security services show as gaps.

Relationship linkerresolves what each asset declares it talks to into typed edges: INVOKES, USES_IMAGE, ASSUMES_ROLE, IAM_TRUST, GRANTS_ACCESS, PROTECTS, MONITORS, MANAGES, GOVERNS, LOGS_TO, ROUTE, LOAD_BALANCER_TARGET, CONTAINS, each with a fine-grained ontology relationship. Resolution is scoped to account and region; references into unmapped accounts become external account nodes

Outputs: inventory-map.json (assets, interconnections, unresolved references, summary), inventory-map.graphml, inventory-graph.json, inventory-dependencies.json (shared dependencies, blast radius, cross-account edges, security coverage) and, with --org, inventory-organization.json. With --findings, additionally asset-map.json (per-asset risk, riskiest first) and compliance-map.json (framework → affected assets). The map never depends on the scanners; findings merge in whenever they exist. Every file is specified field by field in the inventory reference.

Control Tower: run from the management account. Member accounts are reached through AWSControlTowerExecution by default, which is an administrator role; deploy a read-only role (SecurityAudit + ViewOnlyAccess) with a StackSet and pass --org-role for production use.

The same capability is library API: engine.map_inventory(), or cloudg.inventory.InventoryMapper, RelationshipLinker, DependencyGraph and discover_organization standalone. See Python API.

cloudg deps

Interdependency queries over a saved map, no cloud access needed. Each edge reads "dependent needs dependency": a function needs its role, image, key and the queue that triggers it; an ALB needs the WAF protecting it; a resource needs the stack managing it.

cloudg deps arn:aws:iam::123456789012:role/app-role         # both directions
cloudg deps jobs-queue --direction down --depth 5            # blast radius
cloudg deps --map ./reports                                  # shared dependencies, blast radius, cross-account edges
cloudg deps my-function --direction up --json

cloudg ingest

Aggregation without execution. Feed cloudg the native output files of scans that already ran (in CI, on another host, on a schedule) and it runs the normalisation half of the pipeline: cross-scanner dedupe via the check-equivalence rulesets, compliance mapping and report generation. No scanner executes and no cloud credentials are needed.

cloudg ingest \
  --prowler ./prowler-output/ \
  --scoutsuite ./scoutsuite-report/ \
  --checkov ./results_json.json \
  --trivy ./trivy-image.json --trivy ./trivy-fs.json \
  -o ./reports

Every input flag is repeatable and any combination or subset of tools works: one tool alone, or all four together. The exact formats are pinned down under Input requirements.

Ingest runs no collection, so outputs that need live assets (topology, ontology, RAG, Terraform) stay empty. With credentials available, combine both through the API: collect() + ingest_reports() + analyze().

cloudg report

Re-render reports from a previous run's findings.json. No cloud, no scanners. --format takes html, json, svg or all.

cloudg report -i ./reports/findings.json --format html

Input requirements

What each ingest path expects, and the command that produces it.

Prowler

prowler aws -M json-asff -o ./prowler-output

cloudg accepts the output directory or any single file from it, as a JSON array or JSONL. The fields read from each ASFF finding:

{
  "Id": "prowler-aws-s3_bucket_default_encryption-123456789012-eu-west-1-...",
  "Title": "S3 bucket default encryption",
  "Severity": {"Label": "HIGH"},
  "Resources": [{"Id": "arn:aws:s3:::my-bucket"}],
  "Compliance": {"Status": "FAILED", "RelatedRequirements": ["CIS 2.1.1"]},
  "Remediation": {"Recommendation": {"Text": "..."}}
}

Findings with a PASSED status are skipped. The check name embedded in Id becomes the dedupe key.

ScoutSuite

scout aws --report-dir ./scoutsuite-report --no-browser

Accepts the report directory (searched recursively for scoutsuite_results*.js) or the file itself. The file is JavaScript, a JSON object assigned to a variable; cloudg strips the assignment and parses the JSON. Each entry under services.<service>.findings with flagged_items > 0 yields one finding per flagged item. level maps to severity: danger is CRITICAL, warning HIGH, caution MEDIUM.

Checkov

checkov -d ./iac --output json > results_json.json

Accepts the JSON file or a directory containing results_json.json. Both output shapes parse: a single {check_type, results} object, or a list of them when several frameworks ran. Findings come from results.failed_checks[], reading check_id, check_name, severity, resource, file_path and guideline.

Trivy

trivy image --format json myrepo/app:latest > trivy-image.json
trivy fs --format json --scanners vuln,misconfig,secret ./iac > trivy-fs.json

Accepts a single JSON file or a directory of them. The top-level ArtifactType decides the parser: container_image goes through the image parser (vulnerabilities and secrets), everything else through the filesystem parser, which also handles misconfigurations. ArtifactName becomes the resource identifier, and the CVSS v3 score is read when present.

Data models

Everything flowing through cloudg is a Pydantic v2 model from cloudg.schema.models. All models allow extra fields, so scanner-specific attributes survive serialisation.

Finding

resource_id, resource_arnstrinternal ID and cloud-native identifier

The rest

CloudAsset carries arn (the stable identifier; id is regenerated each run), name, a 156-value asset_type taxonomy (EC2, LAMBDA_FUNCTION, CONTAINER_REGISTRY, K8S_WORKLOAD, IAM_ROLE, THREAT_DETECTOR, ORG_UNIT, ...), provider, region, account_id, tags, metadata (with declared relations and aliases on inventory assets) and is_internet_exposed. NetworkEdge is a directed edge with an edge_type (network: SECURITY_GROUP_RULE, NACL_RULE, ROUTE, PEERING, LOAD_BALANCER_TARGET, INTERNET_EXPOSED; structure: CONTAINS, ATTACHED_TO, REFERENCES; identity: IAM_TRUST, IAM_POLICY_ATTACHMENT, ASSUMES_ROLE, GRANTS_ACCESS; workload: INVOKES, USES_IMAGE, LOGS_TO; security and governance: PROTECTS, MONITORS, MANAGES, GOVERNS), a fine-grained ontology relationship, properties, and ports, protocol and CIDR for network rules. ComplianceResult is one control-level verdict with framework, control_id, status and the finding_ids behind it. ScanResult is the aggregate container the normaliser returns and the renderers consume, with a computed summary.

In code, the same structure is CloudGConfig:

from cloudg import CloudGConfig, load_config

config = load_config("config.yaml")
config = CloudGConfig(providers=["aws"])
config.scanners.enabled = ["prowler", "iam"]

aws.max_retries and aws.retry_mode drive botocore's retries since 0.6.0 (they used to be ignored). botocore counts retries after the first attempt, so the default of 10 allows up to 11 attempts per call.

Rate limits

A map of an AWS Organization sends thousands of read-only calls into every member account, and an AI agent can ask for another live map a minute after the last one. Since 0.6.0 every cloud API call goes through cloudg.resilience, one governor shared by every client in the process:

  • Token buckets per account x region x service, per API action for EC2, per subscription and resource provider on Azure, per project or organization and RPC on GCP. The defaults sit at or below each provider's published limits: 20 rps per AWS service and per EC2 action, 20 rps per Azure subscription, 3 rps per user for Resource Graph, 1.5 rps for Cloud Asset ListAssets.
  • A throttled scope is halved for every client using it and paused for the server's Retry-After, then recovers by 5% of its ceiling every five seconds without throttling.
  • At most 128 requests are in flight per AWS account, 16 per Azure subscription or GCP project (max_concurrency).
  • A service, or an EC2 action, still failing after its retries five times in a row is skipped for 60 seconds by a circuit breaker; then one probe call goes through. A throttled DescribeSubnets does not block DescribeVpcs.
  • Retries use decorrelated jitter and never undercut Retry-After. botocore, azure-core and google-api-core keep doing their own retrying, configured by cloudg and reporting back to it. Once the provider's shared retry budget is spent, every call still gets its first two retries and no more.

Throttling never fails a map. A service that stayed throttled shows up in coverage as FAILED or PARTIAL with an error starting throttled:, and the run's numbers land in InventoryResult.throttling, in summary["throttling"] and in inventory-map.json:

aws/123456789012/us-east-1/ec2: throttled 11x, slowed to 5.0 rps, 10 retries, 1 calls gave up

Tune it under ratelimit; unset limits keep the built-ins and service overrides merge into them:

ratelimit:
  aws:
    account_max_rps: 40                  # all services of one account together
    services:
      resourcegroupstaggingapi: { max_rps: 1, burst: 2 }
      ec2.DescribeImageAttribute: { max_rps: 5, burst: 10 }
  live_cooldown_seconds: 600            # MCP live collections, per scope

A misspelled key under ratelimit is logged as unknown and ignored. ratelimit.enabled: false turns it all off; botocore's own retries remain. The rate limits and throttling guide covers the architecture, the per-provider wiring, the built-in limits with their sources, every key, a throttled run's output, the Python API (call_with_resilience, @resilient, stats_scope, LiveOperationGuard) and tuning.

Python API

CloudGEngine in cloudg.api is the integration entry point: async-first, sync wrappers included, built for embedding in larger systems (SIEM pipelines, orchestration platforms, command extensions such as hol-guard).

from cloudg import CloudGConfig, CloudGEngine

engine = CloudGEngine(CloudGConfig(providers=["aws"]))
engine.on_finding = lambda f: siem.send(f.model_dump(mode="json"))
engine.on_error = lambda phase, exc: alerting.notify(phase, exc)

result = engine.run_pipeline_sync()
print(result.to_summary())
MethodReturnsDoes
collect()CollectionResultmulti-provider asset collection: assets, edges, coverage
scan(assets, edges)list[Finding]enabled scanners in parallel, plus reachability and IAM linting
ingest_reports(reports)list[Finding]parse existing scanner outputs; nothing executes
normalise_findings(findings)ScanResultdedupe, cross-scanner merge, CVSS rescoring, compliance mapping
analyze(assets, edges, findings)AnalysisResultgraph, ontology, RAG chunks, Terraform, attack paths
run_pipeline()PipelineResulteverything, end to end; run_pipeline_sync() for non-async callers
run_from_reports(reports)PipelineResultingest, normalise, report in one call; sync twin available
map_inventory()InventoryResultscanner-independent inventory mapping: deep collection, catch-all sweeps, relationship linking; sync twin available

Event hooks: on_phase_start(phase), on_collection_complete(result), on_finding(finding), on_scan_complete(findings), on_analysis_complete(result), on_error(phase, exc). Exceptions raised inside a hook are swallowed, so a broken callback cannot take the pipeline down. PipelineResult carries the data, report paths, coverage and a to_summary() dict ready to serialise.

Integration recipes

Aggregate existing scan results, get reports

engine = CloudGEngine(CloudGConfig())
result = engine.run_from_reports_sync(
    {"prowler": ["./prowler-output/"], "trivy": ["./trivy-image.json"]},
    output_dir="./reports",
)
print(result.total_findings, result.severity_breakdown)
print(result.report_paths["html"])

Parse first, decide later

from cloudg.ingest import ingest_reports

findings = ingest_reports({"prowler": ["./out/"], "checkov": ["results_json.json"]})
scan_result = engine.normalise_findings(findings)

for c in scan_result.compliance:
    if c.status.value == "FAIL":
        print(c.framework, c.control_id, len(c.finding_ids))

The per-scanner parsers are also public: TrivyScanner.parse_report("./trivy.json") and friends, one tool with no engine.

Map the inventory, overlay findings later

inventory = engine.map_inventory_sync(output_dir="./reports")   # no scanners
print(inventory.summary["assets_by_service"])   # what exists
print(inventory.summary["internet_exposed"])    # what faces the internet

# hours or days later, when scanner output exists:
findings = engine.ingest_reports({"prowler": ["./ci-prowler-output/"]})
InventoryMapper(config).export_merged(inventory, findings, "./reports")
# -> asset-map.json, compliance-map.json

Combine live collection with ingested reports

collection = await engine.collect()
ingested = engine.ingest_reports({"prowler": ["./ci-prowler-output/"]})
scan_result = engine.normalise_findings(ingested, assets=collection.assets)
await engine.analyze(collection.assets, collection.edges, scan_result.findings)

Gate a CI job on severity

result = CloudGEngine(CloudGConfig()).run_from_reports_sync(
    {"checkov": ["results_json.json"]}
)
if result.severity_breakdown.get("CRITICAL", 0):
    sys.exit(1)

Plugins

Custom collectors and scanners register through setuptools entry points; no core changes needed. PluginRegistry discovers them at startup and falls back to the built-ins for any name not overridden.

# my_package/scanner.py
from cloudg.schema.models import Finding, Severity

class MyScanner:
    def run(self) -> list[Finding]:
        return [Finding(
            resource_id="arn:aws:s3:::example",
            severity=Severity.HIGH,
            title="Example finding",
            description="What was found and why it matters",
            source_tool="myscanner",
            source_finding_id="MY_CHECK_001",
        )]
[project.entry-points."cloudg.scanners"]
myscanner = "my_package.scanner:MyScanner"

[project.entry-points."cloudg.collectors"]
mycloud = "my_package.collector:MyCollector"

After pip install, the name works in scanners.enabled and --scanners. If your scanner emits a stable check ID in source_finding_id, add it to cloudg/rules/check_equivalence.yaml so its findings merge with equivalent checks from other tools.

Authentication

Every provider supports several methods, resolved in fixed priority order, so the same config works on a laptop, in CI and on cloud compute.

ProviderMethods, most explicit first
AWSdirect keys; OIDC web identity federation (--aws-role-arn with --aws-web-identity-token-file, the GitHub Actions and EKS pattern); named profile including SSO; the default chain. STS assumption layers on top with --aws-external-id for the third-party auditor pattern, and multi-account fan-out uses accounts plus role_name.
Azureworkload identity federation; service principal with secret or certificate; managed identity; the DefaultAzureCredential chain, which covers az login.
GCPcredentials file (service account key or workload identity federation config); application default credentials. --gcp-impersonate-sa layers impersonation on either.

MCP server

cloudg 0.6.0 is also a Model Context Protocol server. An AI agent (Claude Desktop, Claude Code, Cursor, VS Code or your own) can load an inventory map or a findings report, search and inspect assets, walk the relationship graph, ask for attack paths and blast radius, review findings and compliance gaps, query the ontology and, where the policy allows it, start live collections.

Everything sits in one class, cloudg.mcp.CloudGMCPLayer. Whichever way a request arrives (stdio, HTTP, an MCP server you mounted cloudg into, or a direct Python call), it passes through the same policy: access rules, rate limits, redaction, pseudonymisation, projection and annotation.

ModeEntry pointUse it when
Standalone servercloudg mcp serveyou want cloudg as its own MCP server for a desktop client or a gateway
Mountedlayer.register_into(server)you already run an MCP server (official mcp SDK 1.x or 2.x, or fastmcp 2, 3 or 4)
In-processawait layer.call_tool(...)you are writing Python and do not need MCP on the wire
pip install cloudg            # the layer, the CLI and the dependency-free native server
pip install "cloudg[mcp]"     # + the official mcp SDK: sdk flavor and register_into(...)
pip install fastmcp           # only for the fastmcp flavor or mounting into fastmcp

The full guide is MCP.md; the catalog is in MCP_TOOLS.md, policies and transforms in MCP_PRIVACY.md, and the design in MCP_INTERNALS.md.

# stdio: the desktop client launches the server
cloudg mcp serve --dataset prod=./reports/inventory-map.json

# the snippet to paste into claude-desktop, claude-code, cursor or vscode
cloudg mcp config --client claude-desktop --dataset prod=./reports/inventory-map.json

# streamable HTTP on 127.0.0.1:8765/mcp, bearer token mapped to a role
cloudg mcp serve --transport http --auth-token env:CLOUDG_MCP_TOKEN:analyst

cloudg-mcp and python -m cloudg.mcp run the same commands. Transports: stdio, streamable HTTP and the deprecated SSE endpoints. The server speaks both protocol eras on one object: the handshake versions 2024-11-05, 2025-03-26, 2025-06-18 and 2025-11-25, and the stateless 2026-07-28. --flavor chooses the implementation: native (standard library only), sdk (the official SDK's low-level server), fastmcp, or auto, which uses the SDK when it is installed.

HTTP binds to loopback by default and checks Origin and Host. Before binding anything else, set --auth-token, --allowed-host and --allowed-origin.

Embedding it

Mount every tool, resource and prompt into a server you already run. The host keeps its own tools, and names cloudg does not own still reach the host's handlers. Mount after the host has registered them.

from mcp.server.mcpserver import MCPServer      # mcp 2.x; FastMCP on mcp 1.x works the same
from cloudg.mcp import CloudGMCPLayer

server = MCPServer("platform-tools")
layer = CloudGMCPLayer(policy="standard")
layer.workspace.load("inventory/inventory-map.json", "prod")
layer.register_into(server, prefix="cloudg_")

Or call it in-process, no MCP on the wire:

layer = CloudGMCPLayer(policy="strict")
await layer.call_tool("load_dataset", {"path": "inventory/inventory-map.json", "name": "prod"})
res = await layer.call_tool("find_assets", {"internet_exposed": True})
res.structured["items"]                     # identifiers pseudonymised under strict

The mcp extra pins mcp>=1.30,<3; this release was verified with mcp 1.30.0 and 2.3.0, and fastmcp 2.14.7, 3.4.8 and 4.0.11. Mounting into MCPServer or FastMCP (and into fastmcp) goes through private attributes that a later SDK release can rename, so pin the minor version you tested for that path. The low-level Server path and the native flavor do not depend on them.

Policies & privacy

--policy takes a built-in profile, a YAML or JSON file, or inline JSON. The default is standard.

ProfileIn shortTools (local user)
openno restrictions and no transforms, for trusted local use74
standardsecrets redacted, private keys dropped, credential ids masked, attacker-controllable text fenced, secrets in arguments refused; reveal_token only for admin and privacy-admin73
strictas standard, plus pseudonymised identifiers, IPs, e-mails and tag values, rate limits on every tool, and no live, export or restricted tools61
read_onlyas standard, without cloud access, processes or file writes66
airgappedas standard, without cloud access or processes69
auditas read_only, every call logged, risk annotations inline66
soc-analystrole-based example: analysts see pseudonyms, the lead role sees clear values62; analyst 60, lead 70

Pseudonyms round-trip: an agent can pass a pseudonymised ARN back as an argument and the input pipeline reverses it. Set CLOUDG_MCP_VAULT_KEY to keep them stable across restarts; a policy with vault.path also saves the vault when the server shuts down. reveal_token, for the roles allowed to use it, turns a pseudonym or an alias back into the real value. Policies extend each other and carry per-role rules, sensitivity ceilings, per-principal rate limits and transform pipelines; the details are in MCP_PRIVACY.md.

The four live tools (map_inventory, collect_assets, run_scanners, run_pipeline) use the server's own cloud credentials, whoever calls. They check those credentials first (preflight, at most 25 seconds), then run under the live operation guard: identical concurrent calls share one run, a scope collected in the last two minutes is refused with retry_after_seconds and a loaded live dataset of the same providers to use instead, and at most one live operation runs per scope and two overall. admin and operator can pass force=true to skip the cooldown. Each live tool's answer reports any throttling during its run. rate_limit_status and cloudg://ratelimit show the state; see Rate limits.

Changelog

Every release, newest first. The full detail lives in CHANGELOG.md.

0.6.0 2026-10-09

MCP server and throttling resilience

cloudg is now a Model Context Protocol server. cloudg mcp serve (also cloudg-mcp) exposes 74 tools, 13 resources, 11 resource templates and 11 prompts over stdio or streamable HTTP, on both MCP protocol eras (2024-11-05 to 2025-11-25, and 2026-07-28), with a dependency-free native server or the official SDK. The same layer mounts into an existing MCP SDK or fastmcp server, or runs in-process. Seven policy profiles control access and transform the data on its way out: redaction, pseudonyms that round-trip, fencing of attacker-controllable text, projection and annotation. Live collections check credentials first and run under a guard with single-flight, cooldowns and concurrency caps.

Every cloud API call now goes through cloudg.resilience: shared adaptive token buckets per account, region and service, concurrency caps, Retry-After, circuit breakers per service (per action for EC2) and retries bounded by a shared budget. Throttled services are recorded in coverage as throttled: ... instead of failing the map, and InventoryResult.throttling reports what happened. New ratelimit config section; aws.max_retries and aws.retry_mode are now honoured. New mcp extra (mcp>=1.30,<3), included in all.

The graph analysis reports different results for the same estate. Internet exposure follows network-flow edges only (rules, routes, peering, load balancer targets, attachments to security groups, VPC and subnet containment), so an IAM grant or an API Gateway invoking a Lambda function no longer makes a resource internet-exposed. Entry points are 0.0.0.0/0, ::/0 and the Azure Internet, Any and * sources. Sensitive ports are matched as numbers, so all-traffic rules, Azure * and comma lists report SSH and RDP, 2200-2300 no longer counts as port 22, and egress rules report nothing. Security groups, NSGs, NACLs and target groups are no longer reported as unexpected exposed resources. Finding ids are a hash of the rule and the asset's ARN, the same on every scan. GraphBuilder merges parallel rules between the same two nodes instead of keeping only the last one, which had hidden SSH open to the world behind a later rule for port 443. AWS security group rule edges point at the security group asset. In the ontology, containment and protection relations now point the right way and match both endpoint types, a generic CONTAINS relation brings the total to 64, port relations are read from the parsed ranges, and ENCRYPTED_BY_KMS links an asset to its key. The ontology and RAG exports attach findings to assets by ID, ARN, unique name or unique ARN tail.

0.5.3 2026-10-04

URL sanitization fix

A security fix for CodeQL "incomplete URL substring sanitization" alerts. The GCP relation extractors identified a resource's API service with string prefix tests on host-like literals (cloudkms.googleapis.com/, //iam.googleapis.com/, //sqladmin.googleapis.com/, //container.googleapis.com/). They now parse the service out of the name with anchored regular expressions. Behaviour is unchanged, which was checked against the previous implementation on about 92,000 generated inputs.

0.5.2 2026-10-04

Inventory documentation

The inventory mapper is documented in full: the inventory reference specifies every return structure and exported file field by field with annotated examples, the inventory catalog covers all 156 asset types with their metadata and relationships, and inventory internals explains how the mapper works and how to extend it. No code changes.

0.5.1 2026-10-04

Deep inventory: interdependencies, every account, every service

The inventory map now follows workloads into containers and Kubernetes (ECR, ECS services and task definitions, EKS nodegroups, Fargate, addons, access entries, pod identity, and the Deployments, Services, Ingresses and ServiceAccounts inside clusters), through serverless and event wiring (Lambda triggers and URLs, API Gateway, SQS, SNS, EventBridge, Step Functions, Kinesis), across the full IAM graph and Identity Center, and into the security services and scanners watching the estate, including where they are not enabled. AWS now has 133 collectors plus a Cloud Control API sweep that lists every listable resource type, tagged or not; Azure is read through Azure Resource Graph across every subscription and management group; GCP through Cloud Asset Inventory across the whole organization.

cloudg map --org maps every account of an AWS Organization / Control Tower landing zone (OU tree, SCPs, landing zone, governed regions, controls). Edges are typed (INVOKES, USES_IMAGE, ASSUMES_ROLE, GRANTS_ACCESS, PROTECTS, MONITORS, MANAGES, GOVERNS, LOGS_TO) and cloudg deps answers what an asset needs and what breaks with it. Type maps moved into YAML catalogs. Fixes include global services duplicated per region, a single Azure NSG rule discarding a whole subscription, a GCP state-field crash that truncated projects, and CodeQL / Codacy security findings.

0.5.0 2026-09-30

Inventory mapping

A scanner-independent inventory mapper: cloudg map and CloudGEngine.map_inventory() deep-collect everything deployed or default across AWS, Azure and GCP (network fabric included, with catch-all sweeps so every service appears) and link it into one map. Scanner findings merge in afterwards as asset-map.json and compliance-map.json. The relationship linker, deep collectors and mapper are all public API.

0.4.1 2026-09-29

Security hardening

A pass over the Checkov and Codacy findings: the Docker image runs as a non-root user with a healthcheck, the installers no longer pipe downloads straight into a shell, third-party GitHub Actions are pinned to commit SHAs, plugin loading validates module:Class paths, swallowed errors are logged, and log messages no longer place credential-like words next to runtime values.

0.4.0 2026-09-29

Ingest mode

cloudg now works entirely from scanner outputs you already have: the cloudg ingest command, public parse_report() parsers on all four scanner wrappers, and ingest_reports() / normalise_findings() / run_from_reports() on the engine. No cloud credentials, no scanner binaries. Plus this documentation and a least-privilege fix to the publish workflow.
